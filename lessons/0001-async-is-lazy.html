Lesson 0001 · Async Rust

Async is lazy

One idea that unlocks Tokio: calling an async fn builds a future — it does not run the body until you .await it.

Why this matters for your mission

Interviewers and code reviews both poke this exact point. If you treat async fn like a normal function call, you will write code that “silently does nothing,” misread stack traces, and struggle with the mini-Redis tutorial. Nail laziness first; TCP comes next.

The picture

In synchronous Rust, do_work() runs the body immediately. In async Rust, do_work() returns a value that represents the work — a future. The body runs only when something drives that future, usually by .awaiting it on a runtime (Tokio).

Primary source: Tokio tutorial — Hello Tokio (“Using async/await”).

See it in this repo

Open src/main.rs. The important shape (from the Tokio tutorial) is: 

async fn say_world() {
    println!("world");
}

#[tokio::main]
async fn main() {
    let op = say_world(); // body has NOT run yet
    println!("hello");
    op.await;             // NOW "world" prints
}

Expected output order:

hello
world

Try it: from the repo root, run cargo run. Confirm hello prints before world. Then delete the .await line, run again, and notice world never appears — Rust may even warn that the future is unused.

What #[tokio::main] is doing

An async fn main cannot start by itself. Tokio’s #[tokio::main] macro turns it into a normal fn main that creates a runtime and block_ons your async main. The runtime is the engine that polls futures when they are ready to make progress.
